# Engineering review: what to keep, what to prove

**Decision, 20 November 2026:** keep the Rust scanner, native report, independent catalog and reference harness. Develop the report service as a separately deployable consumer. Start with a shadow pilot on one production repository. The evidence does not support switching off an existing SonarQube installation.

The [integration and public replay](qualification-2026-11-20.md) records which of the original PRs landed and what the resulting scanner matched on public code. This review below describes the starting revision.

## What was reviewed

The starting point was GitHub’s default branch, `108877fa702b02f5c50a5dc37308a75de3b031ef` (8 October), one commit after the published `v0.11.1` tag (`56279c1`). The original tree had 16 workspace members and 366,406 lines across 1,454 workspace Rust files, including tests, excluding vendor code and oracle fixtures. The review followed the data from source discovery and compiler context through findings, metrics, gates, exports, ingestion, persistence and human review. It also covered the lockfile, release archive, CI rules and outstanding changes. It was not a line-by-line verification of every detector.

## Findings and changes

**1. Detector count overstates readiness.** The auditor counts implementation and test markers. On the starting revision it displayed 100% for Java and Ruby because the actionable denominator was zero. The new denominator is *all frozen keys*: at the reviewed baseline that yielded 0/733 for Java and 0/42 for Ruby. Ruby PR #898 subsequently added two tested keys. Strict mode can still allow explicitly documented infrastructure gaps. The other six catalog languages have 1,931 tested keys; the separate GitHub registry has 108/382 implemented queries. Native Java/Ruby checks exist under other contracts. Neither a marker nor a passing test is a reference match.

Rust illustrates the practical risk. In the captured S1612 case, renaming a closure parameter from `s` to `c` or changing only its indentation removed the finding; all variants compiled and produced the same output. The [Rust frontend](../../crates/hoonarqube-rust/src/lib.rs) uses exact source-line anchors for selected contracts. Adding more literal examples could improve a fixture score without improving the analyzer. Replace those cases with general syntax/semantic detectors or label their scope explicitly. Pair rule tests with renamed, reformatted and unrelated negative cases.

The [last five-project reference receipt](../../tools/oracle/integrated-package7-qualification-20261008.json) uses SonarQube Community Build 26.9.0.129388. For its captured Zod scope, 587/594 primary findings matched; 578 matched range and message; 445 matched the complete flow comparison. There were 88 native-only and seven missing primary identities. That receipt belongs to its recorded executable and active rule set; fresh unrestricted native finding totals below have a different denominator. Seventeen licensed C# rules lack corresponding Enterprise execution evidence.

**2. A comparison could falsely claim parity.** For a Python file-level finding, a malformed reference with a string in `textRange` used to match a valid file-level finding. The importer now distinguishes an absent range from an invalid present range. The former still verifies a matching file-level finding; the latter emits an input error, writes no success report and exits 2. CLI tests cover malformed, reversed, overflow, partial valid and omitted ranges. This fixes the verification tool; it does not change the affected rule.

**3. The scanner had conflicting views of C# sources.** The cross-file type index reread files even when project analysis had retained their earlier bytes. An edit between those steps could change a finding in the scan already in progress. The [index builder](../../crates/hoonarqube-cli/src/analyze/csharp_index.rs) now consumes the retained source if available and otherwise indexes one file at a time. The regression changes a base class after capture and checks both the captured run and a fresh run. Scans without retained input still do not promise a filesystem-wide atomic snapshot.

**4. The report server depended on every analyzer just to evaluate gates.** The gate algorithm now lives in a [small workspace crate](../../crates/hoonarqube-gates). The old library path is re-exported. The production service imports the evaluator directly, and only its tests import the scanner. Before and after the split, the host's normal dependency graph contained 219 and 84 distinct package entries (including the service); CI now guards the parser-free service build. This is a build dependency reduction, not a server throughput measurement. The CLI's three external formats also have independent modules and tests; they share only checkout-relative path resolution where their behavior agrees.

**5. Database startup could damage version metadata.** The old initializer stamped an unknown database as schema 1. A failed first initialization could leave only some tables. [The initializer](../../crates/hoonarqube-service/src/store/schema.rs) now takes the writer lock before reading the version, creates a new schema atomically and refuses an unknown version or unrecognized unversioned database. On a healthy v1 database the SQLite schema cookie stays unchanged. A missing service index is re-created in the same transaction. Tests also cover rollback and restart. This version check is not a row-by-row integrity audit.

**6. Green historical CI was insufficient release evidence.** CI previously tested scanners and the server separately; the release smoke accepted a server process that merely stayed running until a timeout. The new test submits a real report over authenticated HTTP, restarts the service, checks the complete report and indexed finding, then resubmits and expects the same analysis ID. Both release paths now unpack the actual archive. Script test discovery also brings previously omitted release-condition and benchmark-harness tests into CI. On the original dependency versions the current advisory policy reported nine advisories across six crates. The scoped upgrade includes the compatible SQLite wrapper/binding pair and does not waive any advisory.

## Verification and current performance

The [validation record](verification-2026-11-20.json) binds the source revisions, binary hashes, input commits, exact project arguments, result hashes and raw timings. The final workspace passed **5,364 Rust tests with none ignored**, strict Clippy and rustdoc, formatting, version sync, catalog integrity, and dependency policy. Separately, 179 Python oracle-harness tests, 49 Linux script tests, three action tests, and 19 dashboard/intake tests passed. The pinned v0.3.1 analyzer reported zero Rust S3776 complexity findings. Remote CI was not run for the local branch.

The original main binary and the candidate produced byte-identical stdout, stderr and exit codes in **14 comparisons**: five formats on both complete and malformed input, a positive SARIF finding after a non-BMP character, and native JSON on three pinned projects. Successful scans returned 0; deliberately incomplete scans returned 2. A fresh CLI report also survived authenticated HTTP ingestion, a service restart, and an idempotent retry, both locally and with the checksum-verified previously published Linux archive.

## Outstanding product and operating risks

| Area | Evidence on this branch | Consequence for the first pilot |
|---|---|---|
| Platform compatibility | Native scanner and report API, Sonar Generic Issue Import and CI exports. A SonarScanner protocol, drop-in Web API replacement and project-history importer have not been established | Inventory the customer's integrations and required reports; choose which interfaces to implement or migrate |
| Identity and administration | Static bearer tokens configured at startup; project reader/reviewer/admin and global admin. Loopback HTTP by default. No external login or group lifecycle | Define the required IdP and group-to-project mapping, revocation interval, credential rotation and audit export; test them before shared production access |
| Service scale | A single SQLite connection behind a mutex; synchronous calls from request handlers. Lists are unpaginated; the findings path can query review state per finding and the dashboard renders each returned entry | Benchmark concurrent ingest and filtered findings reads first. Introduce cursor pagination, batched review lookup and bounded database execution before choosing a new database |
| Retention and recovery | Retention soft-deletes analyses. Data remains on disk; project export materializes rows before its size check. REST restore has a 16 MiB request limit | Rehearse database backup/restore including WAL and audit history above that limit. Set a physical-storage and deletion policy. No claim of HA or disaster recovery |
| Resource usage | Per-file parallelism and several source/duplication limits exist. File facts can accumulate before the duplication limit is evaluated; giant/repetitive input is a different workload from the small published fixtures | Measure cold/warm elapsed time, full process-tree peak memory and incomplete exits by language at pilot repository size |
| Maintenance | Rust and Go frontends reached about 9k and 6.6k lines in a single file, including tests; JS/TS and Python already have many rule modules. Formatter, Clippy and high test counts do not detect fixture specialization | Split by rule family when replacing or expanding actual behavior; require cross-file and independently sourced controls, and avoid broad file moves across stacked PRs |

## Recover the open work

The [stack inventory](open-pr-stacks.md) records the 76 PRs open on 20 November: 23 targeting `main` and 53 targeting another PR branch. The longest chain had 18 PRs (#888 through #946). Historical rollups included failures on #934, #951 and #952; a green child only describes the tested parent/child combination. The two open issues, #881 and #895, already have proposed work in #883 and #898. The TLS lock update here includes the rustls version proposed by #912/#952. None of these PRs was merged or closed in this review.

Start integration with a small independent group. For a stack, map parent and child commits, verify which repairs are already present, replay the exact rule/range controls at the combined head, then run the current dependency policy and workspace CI. #934 and #935 have similar titles; inspect their diffs and supersession before choosing a Go base. Reassess #875 against current dashboard, action and restore behavior; avoid reimplementing it from its issue title. Keep the preserved October checkouts until ownership and remaining changes are reconciled.

## Pilot sequence and decision criteria

1. **Shadow one team's CI.** Pick one repository that already runs SonarQube and where the team can supply the required comparison data. Freeze the revision, inputs, exclusions, analyzer/edition, rule activation, compiler context, coverage and gate settings. Run both scanners without making Hoonarqube the merge gate; keep the current system available for rollback. Deliver one report per commit with incomplete scopes and unsupported metrics visible.
2. **Qualify one rule family end to end.** Start with a family the team actually relies on. Compare reference-only and native-only findings separately, plus primary ranges, messages, supporting flows and gate decisions. Include historical false positives, renamed/reformatted variants and unseen production files. A proposed first exit criterion is zero unexplained differences for the team's blocking gate on the agreed corpus and no passing result on a deliberately incomplete scan. The report should list any differences the team explicitly accepts.
3. **Measure the whole CI job.** On the same runners and inputs, record scanner execution and time until the published gate is available; keep cold and warm runs separate. Compare full process-tree memory, CPU, elapsed p50/p95, and correctness digests. Include compiler startup, serialization, upload and server ingestion. Agree the speed and resource budget in advance. A faster run that drops a rule, scope or result fails.
4. **Qualify shared operations before cutover.** Add pagination and bounded concurrency; define login, revocation and operator roles. Use the pilot's measured largest report and concurrency for soak tests; verify retries after restart, project isolation, backup/restore against the agreed RPO/RTO, and a rollback drill. A production database change requires measured evidence that the current storage model misses those targets.

The first milestone is a reproducible report from an actual team pipeline and a gate decision a reviewer can explain. Full feature parity, a distributed service and a production migration are separate decisions.
