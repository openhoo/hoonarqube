# Performance and footprint review — 2026-09-04

Baseline: `d305104` (0.4.2), built from a pristine checkout. Both builds use
Rust 1.96.0 on Linux, Intel Core i9-14900K. Results below are local measurements,
not CI or live SonarQube parity claims.

## Changes

- GitHub Code Quality dispatch now runs the selected queries directly. It
  previously ran every Sonar rule, discarded those findings, and parsed again.
  Python, C#, Go, and Java share their parse with metric collection. JS/TS
  retains separate path-sensitive metric parsing and strict query parsing
  because their grammars differ. Both run on one guarded worker stack.
- Rust files in that profile compute metrics without running Rust rules.
- Ruby's ordinary report computes lexical metrics directly, avoiding unused
  syntax, scope, CFG, and dataflow construction. Its lexical scanner counts
  rows without allocating sets. Malformed Ruby quality input exits before
  constructing flow facts.
- Single-CPU JS/TS analysis reuses one guarded worker instead of starting a
  new parser thread for each file and profile pass. Parallel warning/report
  ordering and worker-start fallback behavior remain covered by tests.
- Rust's macro-array fallback indexes bindings and accesses once with cached
  regexes. It no longer compiles two regexes and scans the remaining source
  for every array. Shadowing, Unicode boundaries, and recovered keyword
  bindings retain regression coverage.
- Sonar and SARIF assembly move completed JSON trees into their documents
  instead of cloning every finding. Sonar collection borrows paths and keys.
  Serialization still completes before stdout is written, preserving the
  no-partial-document behavior on serialization errors.
- The generic dataflow solver compares the previous fact by reference,
  avoiding a full lattice clone on every block visit.
- Release builds use thin LTO and strip symbols. Panic unwinding remains
  enabled. No dependencies or parser versions changed.

## Measurements

Each CLI workload uses one warmup per build, followed by five measured runs
per build in alternating order. Both binaries receive identical paths,
working directory, and CPU affinity. Each run must succeed, emit valid JSON,
and match both stdout and stderr byte for byte. RSS is the Linux `wait4`
child-process high-water mark, including launch overhead; small-process
measurements can be limited by the launcher's memory footprint.

The mixed corpus contains 4,671 files: 922 C#, 72 Go, 802 JavaScript,
662 Python, 1,405 Rust, and 808 TypeScript files. It combines the six checked-in
Sonar fixture projects, `tools/oracle/fixtures`, `crates`, and `xtask` from
the pristine checkout. Synthetic workloads are generated by
[`scripts/benchmark_fixtures.py`](scripts/benchmark_fixtures.py).

| Workload | CPUs | Before | After | Speedup |
|---|---:|---:|---:|---:|
| Mixed corpus, default JSON | 8 | 6.897 s | 6.808 s | 1.01× |
| Mixed corpus, GitHub SARIF | 8 | 6.869 s | 0.445 s | 15.43× |
| Mixed corpus, Sonar import | 8 | 7.003 s | 6.885 s | 1.02× |
| 300 Rust array declarations | 1 | 0.141 s | 0.084 s | 1.68× |
| 64 Ruby files, 30 methods each | 1 | 0.086 s | 0.010 s | 9.00× |
| 4,096 tiny JavaScript files | 1 | 0.205 s | 0.109 s | 1.88× |
| 400 Python files with many findings, Sonar import | 1 | 0.739 s | 0.535 s | 1.38× |

Default mixed-corpus throughput is effectively unchanged. Improvements are
concentrated in profile selection, Ruby metrics, Rust arrays, worker reuse,
and report construction; the synthetic gains are not general repository
speedup claims. The workstation also had unrelated background workloads.

The existing six-language in-memory benchmark was also run three times per
build at 100 iterations per language. Finding totals matched in every run.
C# remains the slowest synthetic analyzer: median throughput increased from
7.10 to 7.30 files/s. Its broader rule execution remains a substantial cost
in the default profile.

The gzip row measures the executable payload, not a published release archive.
Thin LTO increases linking work; no clean-build-time improvement is claimed.
Use an unstripped build for symbolized debugging. Cargo's
[profile documentation](https://doc.rust-lang.org/cargo/reference/profiles.html)
describes both settings and their tradeoffs.

The local `target` inventory was 65 GB, dominated by accumulated debug
dependencies, incremental builds, and coverage artifacts. That is neither a
clean-build measurement nor shipped footprint. Dependency review found
existing transitive duplicates; `cargo deny` accepts them with warnings.

CommonJS, TypeScript assertions, JSX/TSX, declaration files, and uppercase

infrastructure and implementation-coverage boundaries remain explicit.

## Reproduce

Build and retain the baseline binary before applying changes. Run both binaries
against one unchanged checkout; otherwise source edits invalidate the output
comparison. Keep builds and tests out of timed runs.

```bash
python3 scripts/benchmark_fixtures.py /tmp/hoonarqube-perf-fixtures
python3 scripts/benchmark_cli.py \
  --before /path/to/hoonarqube-before \
  --after /path/to/hoonarqube-after \
  --cpus 1 --runs 5 --output /tmp/tiny-jsts.json \
  -- /tmp/hoonarqube-perf-fixtures/tiny-jsts

python3 scripts/benchmark_cli.py \
  --before /path/to/hoonarqube-before \
  --after /path/to/hoonarqube-after \
  --cwd /path/to/pristine-checkout --cpus 8 --runs 5 \
  --profile github-code-quality --format sarif --output /tmp/mixed-github.json \
  -- .oracle/sonar/projects/oracle-py .oracle/sonar/projects/oracle-js \
  .oracle/sonar/projects/oracle-ts .oracle/sonar/projects/oracle-cs \
  .oracle/sonar/projects/oracle-go .oracle/sonar/projects/oracle-rust \
  tools/oracle/fixtures crates xtask
```

The harness requires Linux and Python 3.11 or later, with no third-party Python
packages. It writes every sample, binary hash, output hash, CPU time, RSS, and
median into the requested JSON file. Differences fail the command. These are
manual developer benchmarks; no hosted benchmark matrix was added.

Local raw measurements, output captures, pristine checkout, and build/check
logs are under `target/performance-review-2026-09-04/`.
